### ملف 1 (الأهم): `RawDetectionReceivedConsumer.cs` — "المحقق الميداني"

**المسار:** `src/Services/Pothole/SmartCity.Pothole.Api/Consumers/RawDetectionReceivedConsumer.cs`

> **في جملة:** بيستلم إيفنت `RawDetectionReceived` من RabbitMQ، بيفلتر بس الأنواع اللي road damage (100-199)، بيحدد الخطورة والحي، بيحفظ سجل حفرة جديد في الداتابيز، وبينشر إيفنت `PotholeSaved`.

**بيستلم من مين:** من RabbitMQ — إيفنت `RawDetectionReceived` اللي الـ AI الوهمي نشره في PR #2.
**بيبعت لمين:** بينشر `PotholeSaved` على RabbitMQ — اللي خدمة CostCalculation بتستلمه.

#### الأجزاء المهمة سطر سطر:

**التعريف والكونستركتور (سطر 13-22):**

```csharp

{
```

فاكر في PR #2 الـ consumers كانوا بياخدوا `ILogger` بس؟ هنا ده بياخد **`PotholeDbContext`** كمان — لأنه محتاج يكتب في الداتابيز. الـ DI container بيديله instance من الـ DbContext تلقائياً.

**الميثود الرئيسية — `Consume` (سطر 24-69):**

```csharp

{

        return;
```

**أول سطر: الفلتر.** نفس اللي كان موجود كـ stub في PR #2 — لو الاكتشاف مش road damage (يعني مش بين 100-199) → ارجع. فاكر إن RabbitMQ بيبعت لكل الخدمات (fan-out)؟ الخدمة هنا بتقول "ده مش بتاعي" وبتتجاهله.

```csharp

    var district = ClassifyDistrict(msg.Location.Latitude, msg.Location.Longitude);
```

**خطوتين ذكيتين قبل الحفظ:**
1. **`ClassifySeverity`** — بيشوف الحفرة خطورتها إيه (Low / Medium / High / Critical) بناءً على العمق.
2. **`ClassifyDistrict`** — بيشوف الحفرة في أنهي حي من أحياء إسطنبول (Meram / Selcuklu / Karatay) بناءً على الإحداثيات.

هنشرحهم بالتفصيل تحت. دلوقتي خلينا نكمل المسار الرئيسي.

```csharp
    // SKELETON: real version clusters with ST_DWithin 3–5 m; this stub inserts a new row every time.
    var pothole = new PotholeRecord
    {
        Id = Guid.NewGuid(),
        SourceDetectionId = msg.DetectionId,
        CorrelationId = msg.CorrelationId,
        Location = new Point(msg.Location.Longitude, msg.Location.Latitude) { SRID = 4326 },
        District = district,
        DetectionType = msg.Type,
        Stage = DamageStage.Pothole,
        Severity = severity,
        Confidence = msg.Confidence,

        LastSeenAt = msg.CapturedAt,
        ImageUrls = new[] { msg.ImageUrl }

```

**ده بيبني سجل الحفرة الجديد.** ملاحظات مهمة:

- **الكومنت `SKELETON:`** بيقول إن النسخة الحقيقية هتعمل clustering — يعني لو نفس الحفرة اتصورت أكتر من مرة من عربيات مختلفة، النسخة الحقيقية هتجمعهم في سجل واحد (باستخدام `ST_DWithin` اللي بيقيس المسافة بين نقطتين). بس دلوقتي كل اكتشاف بيعمل سجل جديد.
- **`Point(Longitude, Latitude)`** — خد بالك من الترتيب! في PostGIS النقطة بتتكتب (X, Y) يعني (Longitude, Latitude). ده عكس اللي الناس بتتوقعه (Latitude, Longitude). غلطة شائعة جداً.
- **`SRID = 4326`** — ده نظام الإحداثيات العالمي (WGS84). نفسه اللي الـ GPS بيستخدمه. يعني الأرقام دي إحداثيات حقيقية على الكرة الأرضية.
- **`SourceDetectionId = msg.DetectionId`** — ده بيربط الحفرة بالاكتشاف اللي جاي من الـ AI. كده تقدر تتتبع: الصورة → الاكتشاف → الحفرة.
- **`CorrelationId`** — لسه نفس الـ CorrelationId من أول الصورة! السلسلة مش مقطوعة.

```csharp
    _db.Potholes.Add(pothole);
```

**ضاف الحفرة لقائمة التغييرات.** لسه مش محفوظة في الداتابيز — `Add` بيحطها في "ذاكرة" الـ DbContext بس. الحفظ الفعلي بيحصل في `SaveChangesAsync` تحت.

```csharp
    var saved = new PotholeSaved
    {
        CorrelationId = msg.CorrelationId,
        SourceDetectionId = msg.DetectionId,
        PotholeId = pothole.Id,
        IsNewPothole = true,
        DetectionCount = 1,
        FirstSeenAt = pothole.FirstSeenAt,
        LastSeenAt = pothole.LastSeenAt,

        District = district,
        DetectionType = msg.Type,
        Stage = pothole.Stage,
        Severity = severity,
        Confidence = msg.Confidence,
        ImageUrls = new List<string> { msg.ImageUrl }
    };
```

**ده الإيفنت اللي هينتشر بعد الحفظ.** ملاحظات:

- **`IsNewPothole = true`** — عشان المستقبل: لما الـ clustering يشتغل، ممكن الاكتشاف يبقى update لحفرة موجودة مش حفرة جديدة. الخدمة اللي بتستلم الإيفنت (CostCalculation) بتتشيك: لو مش حفرة جديدة → مش هتحسب تكلفة تاني.
- **`PotholeId = pothole.Id`** — ده الـ ID بتاع الحفرة اللي لسه حفظناها. كده خدمة التكلفة تعرف هي بتحسب لأنهي حفرة بالظبط.

```csharp
    await context.PublishFollowUp(saved, context.CancellationToken);
    await _db.SaveChangesAsync(context.CancellationToken);
```

**السطرين الأهم.** `PublishFollowUp` (نفس اللي اتعلمناها في PR #2) بتنشر الإيفنت على RabbitMQ. بس استنى — هو بينشر **قبل** ما يحفظ في الداتابيز! مش ده خطر؟

لا، لأن الـ **transactional outbox** بيتكفّل بالموضوع ده. الإيفنت مش بيتبعت فوراً — بيتكتب في جدول `OutboxMessage` **في نفس الـ transaction** اللي بتحفظ الحفرة. بعدها MassTransit بيقرا الجدول ده وبيبعت الإيفنت فعلاً. يعني:
- لو `SaveChangesAsync` نجح → الحفرة والإيفنت الاتنين اتحفظوا مع بعض.
- لو `SaveChangesAsync` فشل → ولا الحفرة اتحفظت ولا الإيفنت اتبعت.

مفيش احتمال إن واحد يحصل والتاني لا. **ده الضمان اللي الـ transactional outbox بيديك إياه.**

**تصنيف الخطورة — `ClassifySeverity` (سطر 76-87):**

```csharp
private static SeverityLevel ClassifySeverity(Dictionary<string, string>? metadata)
{
    if (metadata is null || !metadata.TryGetValue("estimated_depth_cm", out var depthStr)
        || !double.TryParse(depthStr, out var depth))
        return SeverityLevel.Medium;

    return depth switch
    {
        < 4 => SeverityLevel.Low,
        < 7 => SeverityLevel.Medium,
        < 10 => SeverityLevel.High,
        _ => SeverityLevel.Critical
    };
}
```

فاكر في PR #2 لما الـ AI الوهمي كان بيحط `estimated_depth_cm` في الـ metadata (عمق الحفرة بالسنتيمتر)؟ هنا بيستخدمه:

| العمق | الخطورة | يعني |
|---|---|---|
| أقل من 4 سم | Low | حفرة صغيرة — مش مستعجلة |
| 4 - 6 سم | Medium | حفرة متوسطة |
| 7 - 9 سم | High | حفرة كبيرة — لازم تتصلح بسرعة |
| 10+ سم | Critical | حفرة خطيرة — ممكن تأذي العربيات |

لو الـ metadata مفيهاش عمق (يعني الـ AI مبعتش) → default يبقى `Medium`.

الـ `switch expression` ده syntax جديد في C# — بدل `if/else if/else` طويلة، بتكتب الحالات بشكل أنضف.

**تحديد الحي — `ClassifyDistrict` (سطر 90-96):**

```csharp
private static District ClassifyDistrict(double lat, double lon)
{
    if (lat < 37.88 && lon < 32.48) return District.Meram;
    if (lat >= 37.88 && lon < 32.50) return District.Selcuklu;
    return District.Karatay;
}
```

**ده stub بسيط.** بيقسم مدينة إسطنبول لـ 3 أحياء بناءً على مربعات (bounding boxes) تقريبية:
- لو الحفرة في الجنوب الغربي → **Meram**
- لو في الشمال → **Selcuklu**
- غير كده → **Karatay**

النسخة الحقيقية هتستخدم **PostGIS polygons** — يعني حدود الأحياء الفعلية المرسومة على الخريطة، مش مجرد مربعات.

> **ملحوظة:** أسماء Meram / Selcuklu / Karatay والإحداثيات اللي في الكود ده من قونيا، بالغلط. ده لأن الـ`District` enum موجود في الـContracts ولسه ماتغيرش. هيتغير مع باقي الـcontracts في PR واحد، وساعتها هيبقى فيه أرقام وأسماء أحياء إسطنبول.

### ملف 2: `PotholeSavedConsumer.cs` — "المحاسب"

**المسار:** `src/Services/CostCalculation/SmartCity.CostCalculation.Api/Consumers/PotholeSavedConsumer.cs`

> **في جملة:** بيستلم إيفنت `PotholeSaved` من RabbitMQ، بيحسب تكلفة إصلاح الحفرة حسب خطورتها (مواد + عمالة + معدات)، بيحفظ التقدير في الداتابيز، وبينشر إيفنت `CostEstimateGenerated`.

**بيستلم من مين:** من RabbitMQ — إيفنت `PotholeSaved` اللي خدمة Pothole نشرته (الملف اللي فوق).
**بيبعت لمين:** بينشر `CostEstimateGenerated` على RabbitMQ — اللي خدمة WorkOrder هتستلمه في milestone لاحق.

#### الأجزاء المهمة سطر سطر:

**التعريف (سطر 11):**

```csharp
public sealed class PotholeSavedConsumer : IConsumer<PotholeSaved>
```

خلي بالك: الـ consumer ده بيستلم **`PotholeSaved`** مش `RawDetectionReceived`! ده الفرق المهم — كل خدمة بتستلم الإيفنت اللي الخدمة **اللي قبلها** بعتته:

```
AI → RawDetectionReceived → Pothole → PotholeSaved → CostCalculation → CostEstimateGenerated → ...
```

ده بيوضح إن الخدمات مش بتكلم بعض مباشرة — كل واحدة بتبعت إيفنت والخدمة التانية بتلقطه. ده الـ **event-driven architecture**.

**التشيك الأول (سطر 27-28):**

```csharp
    var msg = context.Message;

    if (!msg.IsNewPothole)
        return;
```

لو الحفرة مش جديدة (يعني حفرة قديمة اتشافت تاني) → مش هيحسب تكلفة جديدة. التكلفة بتتحسب مرة واحدة بس لكل حفرة.

**حساب التكلفة (سطر 30-31):**

```csharp
    var (total, materialCost, laborCost, equipmentCost) = GetCostBySeverity(msg.Severity);
```

ده بيستخدم **tuple deconstruction** — يعني الميثود بترجّع 4 قيم مرة واحدة وبيحطهم في 4 متغيرات. هنشوف الميثود نفسها تحت.

**بناء سجل التكلفة (سطر 33-57):**


**ده بيبني "فاتورة تقديرية" للحفرة.** ملاحظات:

- **`SourceEntityId = msg.PotholeId`** — بيربط التقدير بالحفرة. خدمة التكلفة مش بتعرف عن الـ potholes table — بس عارفة الـ ID. ده "database per service" — كل خدمة عندها الداتا بتاعتها بس.
- **`SourceEntityType = RoadDamage`** — ليه مش `Pothole` بالاسم؟ لأن خدمة التكلفة هتخدم **كل** أنواع المشاكل: حفر، مخالفات، مباني... كل واحد ليه `SourceEntityType` مختلف. كده الخدمة generic.
- **`EstimatedLaborHours`** — حفرة صغيرة = ساعة شغل، كبيرة = 5 ساعات. أرقام stub طبعاً.
- **`EstimatedCrewSize`** — حفرة كبيرة (High/Critical) محتاجة 3 عمال، صغيرة 2.
- **`SuggestedPriority`** — الخطورة بتحدد الأولوية: Critical → Critical، وهكذا. اسمها "suggested" لأن مسؤول البلدية ممكن يغيّرها.

**جدول الأسعار — `GetCostBySeverity` (سطر 106-118):**

```csharp
private static (decimal total, decimal material, decimal labor, decimal equipment)
    GetCostBySeverity(SeverityLevel severity)
{
    var total = severity switch
    {
        SeverityLevel.Low => 1000m,
        SeverityLevel.Medium => 1800m,
        SeverityLevel.High => 2500m,
        SeverityLevel.Critical => 4000m,
        _ => 1800m
    };

    return (total, total * 0.36m, total * 0.48m, total * 0.16m);
}
```

**ده جدول الأسعار الوهمي** (بالليرة التركية TRY):

| الخطورة | التكلفة الكلية | مواد (36%) | عمالة (48%) | معدات (16%) |
|---|---|---|---|---|
| Low | 1,000 TRY | 360 | 480 | 160 |
| Medium | 1,800 TRY | 648 | 864 | 288 |
| High | 2,500 TRY | 900 | 1,200 | 400 |
| Critical | 4,000 TRY | 1,440 | 1,920 | 640 |

التقسيم ثابت: 36% مواد، 48% عمالة، 16% معدات. النسخة الحقيقية هتقرا الأسعار من كتالوج في الداتابيز أو config.

`m` اللي بعد الأرقام (زي `1000m`) معناها `decimal` — نوع بيانات دقيق للفلوس. مش `float` أو `double` اللي ممكن يعملوا أخطاء تقريب (0.1 + 0.2 = 0.30000000000000004). **الفلوس دايماً بنستخدملها `decimal`.**

### ملف 3: `PotholeRecord.cs` — "بطاقة هوية الحفرة"

**المسار:** `src/Services/Pothole/SmartCity.Pothole.Api/Domain/PotholeRecord.cs`

> **في جملة:** الكلاس اللي بيمثّل صف واحد في جدول `potholes` في الداتابيز — كل الحقول اللي بنحفظها عن حفرة واحدة.

```csharp
public class PotholeRecord
{
    public Guid Id { get; set; }                    // المفتاح الأساسي — UUID فريد
    public Guid SourceDetectionId { get; set; }     // الاكتشاف اللي جاي من الـ AI (ربط للوراء)
    public Guid CorrelationId { get; set; }         // رقم القضية — بيربط كل السلسلة
    public Point Location { get; set; } = default!; // إحداثيات الحفرة (نقطة على الخريطة)
    public District District { get; set; }          // الحي (Meram, Selcuklu, Karatay)
    public string? RoadName { get; set; }           // اسم الشارع (فاضي دلوقتي)
    public DetectionType DetectionType { get; set; } // النوع (Pothole, RoadCrack, SurfaceDamage)
    public DamageStage Stage { get; set; }          // مرحلة الضرر
    public SeverityLevel Severity { get; set; }     // الخطورة (Low → Critical)
    public double Confidence { get; set; }          // نسبة ثقة الـ AI
    public int DetectionCount { get; set; } = 1;    // كام مرة اتشافت (للـ clustering لاحقاً)
    public DateTimeOffset FirstSeenAt { get; set; } // أول مرة اتشافت
    public DateTimeOffset LastSeenAt { get; set; }  // آخر مرة اتشافت
    public PotholeStatus Status { get; set; } = PotholeStatus.Open;  // مفتوحة ولا اتصلحت
    public string[] ImageUrls { get; set; } = Array.Empty<string>(); // صور الحفرة
}

public enum PotholeStatus
{
    Open,    // لسه محتاجة إصلاح
    Fixed    // اتصلحت
```

**التعريف (سطر 12-13):**

`RoadDamageQueryService.RoadDamageQueryServiceBase` ده كلاس اتعمل تلقائياً من ملف `.proto` (protobuf). الـ `.proto` بيعرّف الـ contract — "إيه الميثودز المتاحة وكل واحدة بتاخد إيه وبترجّع إيه". لما تعمل `dotnet build`، الـ proto بيتحول لكود C#. أنت بس بتعمل override للميثودز.

**هات حفرة بالـ ID — `GetDamageById` (سطر 17-27):**

```csharp
public override async Task<DamageDetailResponse> GetDamageById(
    GetDamageRequest request, ServerCallContext context)
{
    if (!Guid.TryParse(request.DamageId, out var id))
        throw new RpcException(new Status(StatusCode.InvalidArgument, "Invalid damage_id"));

    var p = await _db.Potholes.AsNoTracking()
        .FirstOrDefaultAsync(x => x.Id == id, context.CancellationToken);
    if (p is null)
        throw new RpcException(new Status(StatusCode.NotFound, "Pothole not found"));

    return MapToDetail(p);
}
```

- **`RpcException`** — في gRPC مفيش HTTP status codes (404, 400...). بدل كده بتستخدم `StatusCode.NotFound`، `StatusCode.InvalidArgument`... نفس الفكرة بس بمسمى gRPC.
- **`AsNoTracking()`** — بيقول للـ EF Core "أنا بقرا بس، مش هعدّل". ده بيوفر ذاكرة ويسرّع الـ query.
- **`MapToDetail`** — بيحوّل من `PotholeRecord` (الـ entity بتاع C#) لـ `DamageDetailResponse` (الـ protobuf message). ده لازم يحصل لأن gRPC بيرجّع protobuf messages مش C# objects.

**هات قائمة الحفر — `ListDamages` (سطر 29-65):**

```csharp

    ListDamagesRequest request, ServerCallContext context)
{
    var query = _db.Potholes.AsNoTracking().AsQueryable();
```

بيبدأ بـ query فاضي — "هات كل الحفر". بعدين بيضيف عليه فلاتر لو موجودة:


**فلتر بالحي.** لو الطلب قال "عايز حفر Meram و Selcuklu بس" → يضيف `WHERE district IN ('Meram', 'Selcuklu')`.

```csharp
    if (request.MapArea is not null)
    {
        var sw = request.MapArea.SouthWest;
        var ne = request.MapArea.NorthEast;
        var envelope = new Envelope(sw.Longitude, ne.Longitude, sw.Latitude, ne.Latitude);
        var box = new GeometryFactory(new PrecisionModel(), 4326).ToGeometry(envelope);
        query = query.Where(p => p.Location.Intersects(box));

```

**فلتر بالخريطة (spatial query).** تخيل إنك فتحت خريطة على موقع البلدية وزومت على منطقة معينة. الـ frontend بيبعت إحداثيات الزاوية الجنوبية الغربية (SouthWest) والشمالية الشرقية (NorthEast). الكود بيبني مستطيل (envelope/box) وبيسأل الداتابيز "هات كل الحفر اللي جوا المستطيل ده". PostGIS بيستخدم الـ GIST index عشان يلاقيهم بسرعة.

```csharp
    var pageSize = request.Pagination?.PageSize > 0
        ? Math.Min(request.Pagination.PageSize, 100) : 20;
    var totalCount = await query.CountAsync(context.CancellationToken);

    if (!string.IsNullOrEmpty(request.Pagination?.PageToken)
        && Guid.TryParse(request.Pagination.PageToken, out var cursor))
        query = query.Where(p => p.Id.CompareTo(cursor) > 0);

    var records = await query
        .OrderBy(p => p.Id)
        .Take(pageSize)
        .ToListAsync(context.CancellationToken);
```

**Cursor pagination** — بدل الـ page number (صفحة 1، صفحة 2...) بيستخدم cursor. الفكرة:
1. الطلب الأول: "هات أول 20 حفرة" → يرجّع 20 حفرة + الـ ID بتاع آخر واحدة كـ `NextPageToken`.
2. الطلب التاني: "هات 20 حفرة **بعد** الحفرة دي" → `WHERE id > cursor ORDER BY id TAKE 20`.

ده أسرع من `OFFSET/LIMIT` لما الداتا كتير (offset بيسكن كل الصفوف اللي قبل كده).

`Math.Min(request.Pagination.PageSize, 100)` بيحمي من حد يطلب مليون سجل مرة واحدة — الحد الأقصى 100.

### ملف 7: `PotholeDbContext.cs` — "خريطة جدول الحفر"

**المسار:** `src/Services/Pothole/SmartCity.Pothole.Api/Data/PotholeDbContext.cs`

> **في جملة:** بيعرّف الـ EF Core إزاي يخزّن `PotholeRecord` في PostgreSQL — أسماء الجداول، أنواع الأعمدة، والـ indexes.

```csharp
public class PotholeDbContext : DbContext
{
    public DbSet<PotholeRecord> Potholes => Set<PotholeRecord>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.AddSmartCityOutboxEntities();

        modelBuilder.Entity<PotholeRecord>(e =>
        {
            e.ToTable("potholes");
            e.HasKey(p => p.Id);
            e.HasIndex(p => p.SourceDetectionId).IsUnique();
            e.Property(p => p.Location).HasColumnType("geography(Point,4326)");
            e.HasIndex(p => p.Location).HasMethod("gist");
            e.Property(p => p.District).HasConversion<string>();
            e.Property(p => p.DetectionType).HasConversion<string>();
            e.Property(p => p.Stage).HasConversion<string>();
            e.Property(p => p.Severity).HasConversion<string>();
            e.Property(p => p.Status).HasConversion<string>();
            e.Property(p => p.ImageUrls).HasColumnType("text[]");
        });
    }
}
```

أهم الإعدادات:
- **`geography(Point,4326)`** — العمود ده نقطة جغرافية بنظام WGS84. PostGIS بيفهمه ويعرف يعمل عليه عمليات زي "هات كل النقط في نطاق 5 كيلو".
- **`HasMethod("gist")`** — GIST index — فهرس خاص ببيانات الخرائط. بدونه البحث الجغرافي هيبقى بطيء جداً.
- **`HasConversion<string>()`** — الـ enums (زي `District.Meram`) بتتحفظ كنص في الداتابيز مش كرقم. كده لما تفتح الداتابيز تقرا "Meram" بدل "0". وده متوافق مع قاعدة الـ Contracts: "enums go over the bus as strings".
- **`HasIndex(p => p.SourceDetectionId).IsUnique()`** — كل اكتشاف بيعمل حفرة واحدة بس. لو نفس الاكتشاف وصل مرتين (at-least-once delivery)، الداتابيز هيرفض التاني.
- **`text[]`** — نوع خاص في PostgreSQL: مصفوفة نصوص. كده الصور بتتحفظ كـ array في نفس الصف مش في جدول منفصل.

## مفاهيم مهمة اتعلمناها من PR ده

### 1. الـ Transactional Outbox (أهم مفهوم في PR ده)
المشكلة: لازم نحفظ في الداتابيز **ونبعت** إيفنت. لو حفظنا وبعدين الإيفنت فشل (أو العكس) — البيانات هتبقى مش متسقة.
الحل: الإيفنت بيتكتب في جدول `OutboxMessage` **في نفس الـ transaction** اللي بيحفظ الداتا. بعدها MassTransit بيقرا الجدول وبيبعت الإيفنت فعلاً. يا الاتنين ينجحوا يا الاتنين يفشلوا.

### 2. الـ Database per Service
خدمة Pothole عندها `pothole_db` وخدمة CostCalculation عندها `costcalc_db`. مفيش خدمة بتقرا من داتابيز خدمة تانية. محتاج بيانات؟ خدها من الإيفنت اللي على RabbitMQ.

### 3. الفرق بين الكتابة (Events) والقراءة (gRPC)
- **الكتابة** بتحصل من خلال إيفنتات RabbitMQ (async) — الخدمة بتستلم الإيفنت وبتحفظ.
- **القراءة** بتحصل من خلال gRPC (sync) — الـ Gateway بيسأل والخدمة بترد فوراً.

### 4. الـ Cursor Pagination
بدل "هات صفحة رقم 5" (OFFSET) → "هات 20 سجل **بعد** آخر سجل شفته" (CURSOR). أسرع لأن الداتابيز مش محتاجة تعد كل اللي قبل كده.

### 5. الـ Spatial Queries (PostGIS)
`geography(Point,4326)` + GIST index = تقدر تسأل الداتابيز "هات كل الحفر في المستطيل ده على الخريطة" بسرعة. ده اللي بيخلي عرض الحفر على الخريطة في الـ frontend سريع.
