### أهم حاجة تفهمها: التوزيع (Routing) بيحصل إزاي؟

RabbitMQ بيبعت إيفنت `RawDetectionReceived` **لكل** الخدمات (fan-out). بس كل خدمة بتفلتر **جواها** وبتاخد اللي يخصها بس:

```
DetectionType enum:
   Pothole = 100          ──► IsRoadDamage() = (100-199) ──► Pothole service
   RoadCrack = 101        ──╯
   SurfaceDamage = 102    ──╯

   TrafficLight = 200     ──► IsAsset() = (200-299)      ──► Inventory service
   TrafficSign = 201      ──╯
   StreetLight = 202      ──╯

   CommercialSign = 300   ──► IsViolation() = (300-399)  ──► Violation service
   Banner = 301           ──╯

   Scaffolding = 400      ──► IsBuilding() = (400-499)   ──► Building service
   ConstructionSite = 401 ──╯
```

الفلترة بتحصل بميثودز بسيطة في `DetectionType.cs`:

```csharp
public static bool IsRoadDamage(this DetectionType t) => (int)t is >= 100 and < 200;
public static bool IsAsset(this DetectionType t)      => (int)t is >= 200 and < 300;
public static bool IsViolation(this DetectionType t)  => (int)t is >= 300 and < 400;
public static bool IsBuilding(this DetectionType t)   => (int)t is >= 400 and < 500;
```

يعني لو الرقم بين 100 و 199 → ده road damage → يروح لـ Pothole. ذكي وبسيط.

## مفاهيم مهمة اتعلمناها من PR ده

### 1. الـ Fan-out Pattern
RabbitMQ بيبعت الإيفنت الواحد **لكل** الـ consumers اللي مشتركين فيه. الفلترة بتحصل **جوا** كل consumer. ده أبسط من إنك تعمل routing معقد في الـ broker نفسه.

### 2. الفرق بين `PublishEvent` و `PublishFollowUp`
- `PublishEvent` = أنا المصدر (بدأت سلسلة جديدة).
- `PublishFollowUp` = أنا مكمّل على حد تاني (لازم الـ CorrelationId يتنقل صح).

### 3. الـ SKELETON Pattern
الخدمات الأربعة (Pothole, Inventory, Violation, Building) كلها stubs — بتعمل log بس. ده عشان المهم دلوقتي إن **السلسلة كلها تشتغل end-to-end**. التنفيذ الحقيقي لكل خدمة هييجي في milestones بعدين.

### 4. نظام الأرقام (Range-Based Routing)
- 100-199 = Road Damage → Pothole service
- 200-299 = Assets → Inventory service
- 300-399 = Violations → Violation service
- 400-499 = Building → Building service
