The idea

Main record (potholes)

One row per pothole, with its current state: open or closed, the latest severity and size, and the repair status for display. Only this part gets updated.

The observations

A new row each time the pothole is seen, corrected or checked. Rows are only added. They are never updated or deleted.

Think of a patient's file in a hospital: the main record is the cover that shows the condition, and every X-ray goes inside the file. The pothole has no repair steps. Those all live in Work Order. The pothole only keeps a display-only copy of the ticket status, and no rule depends on it.

What each method does

MethodCalled fromWhat it doesEmits
FromDetectionAn AI detection with no open pothole nearbyA new Open pothole, and its first observation of kind "AI detection"PotholeSaved (new)
AddedByOfficerThe officer added a pothole (P1)A new Open pothole, and an observation of kind "officer add". The confidence check and the 30-day rule do not apply to itPotholeSaved (new)
AddSightingA detection next to an open potholeA new observation, and the main record is updated. Returns true if the severity or the stage changedPotholeSaved (changed), only if true
AddReportThe officer added a report next to an open potholeAn observation of kind "officer add" on the existing potholeNone
CorrectThe officer corrected the data (P2)An observation of kind "correction" with the reason, and the main record and the estimate are updated. Rejected if the pothole is closedPotholeSaved (corrected)
RecordVerificationThe RepairVerificationObserved messageAn observation of kind "verification pass" with the result and the image. Does not change the statusNone
ApplyRepairStatusAny message from Work OrderWrites the ticket status into the display-only copy, but only if the pothole is open and ticket_sequence is bigger than the one it has. If the pothole is closed, the message is ignoredNone
CloseThe ticket is Completed or Cancelled, or DetectionDismissedThe pothole becomes Closed with the reason, after ApplyRepairStatus writes the last repair status. If it is already closed, it does nothingNone

Every method increases RowVersion by one. So if two writers change the same pothole at the same moment, the second one is rejected. If any rule is broken, the method throws an exception and nothing changes.

  • Matching (PotholeMatcher): Looks for an Open pothole within 3 meters only. The number is in the config and can be changed. The IsSuppressed method tells if a pothole in this place was closed as a "mistake" less than 30 days ago. In that case the AI detection is only saved as an observation on that pothole.
  • The estimator (PotholeEstimator): Pothole's own static class. It is called when a pothole is created or when its severity or stage changes. The prices come from the config and are passed in. Inventory and Building will have their own estimators, because each kind of thing is repaired in a different way. Only the shape of the result (CostEstimate) is shared, through the Contracts.
  • The dismissed detection: Has no table. The DetectionDismissed message has the pothole id. The pothole always exists, because it is created before the officer sees the detection. So Pothole closes it right away. Decided
  • Recurring spots (RecurringSpot): Not part of the pothole. The job computes them and writes them again from scratch each time. They are for statistics only (P17).

  • Districts and neighborhoods (admin_areas): The districts (admin_level 6, ilçe) and neighborhoods (admin_level 8, mahalle) of Istanbul, loaded once from OpenStreetMap GeoJSON. When a pothole is created, it gets district_id and neighborhood_id from a point-in-polygon check (Intersects).

Tables not in the diagram

  • processed_idempotency_keys: so that an officer command sent twice returns the same response.
  • inbox_state, outbox_message and outbox_state: MassTransit creates and manages them by itself.

The sightings_count column counts AI detections only, meaning how many times vehicles saw the pothole. Corrections, officer adds and verification passes do not increase it. Decided It exists so the "how many times seen" filter works without counting the observations every time. The confidence on the main record is the confidence of the last detection.

Constraints and indexes

These constraints protect the rules even if there is a bug in the code.

TableConstraint or indexWhat it protects
potholesPartial GIST on location when status = OpenFast matching: "Is there an open pothole within 3 meters?"
potholesPartial GIST on location when closed_reason = FalsePositiveThe 30-day rule: "Was a pothole near here closed as a mistake?"
potholesGIST on location for all potholesThe map, and the recurring spots job
potholesrow_version as a concurrency tokenTwo people change the same pothole at the same moment: the second one gets 409, or the message is retried
potholescheck: if status = Closed, then closed_reason and closed_at are not empty. If Open, they are emptyA closed pothole with no reason
potholescheck: if closed_reason = Duplicate, then duplicate_of_id is not empty and is not equal to idA "duplicate" with no original pothole, or a pothole that is a duplicate of itself
potholesindex on (district_id, status), on repair_status, and on last_seen_atLists, filters and sorting
potholescheck: area_m2 > 0, depth_cm > 0, est_total >= 0, and confidence between 0 and 1Wrong numbers
observationsunique on source_detection_id when it is not emptyThe same detection is not saved twice
observationsindex on (pothole_id, seen_at desc)The pothole history, newest first
observationscheck: verification_result is not empty only when kind = VerificationPassA verification result on a row that is not a verification
recurring_spotsGIST on location, and index on districtThe statistics screen
admin_areasGIST on geometryFind the district and neighborhood of a point

There is no unique constraint on the pothole location, because a closed spot becomes a new pothole. Until the lock is built, two potholes may be created at the same moment. The officer then closes the duplicate with duplicate_of_id. Deferred

How data is saved

The same pothole at 5 moments, and what is written to the tables each time:

What happenedpotholesobservations
The vehicle saw a new crackNew row P1: Open, stage 1, sightings_count = 1Row: AI detection, stage 1
Seen again, and it became a potholeP1: stage 4, sightings_count = 2Row: AI detection, stage 4
Work Order opened a ticket, and the crew arrivedP1: work_order_id is filled, and repair_status = OnSiteNone
The vehicle passed twice after the repairNoneTwo rows: verification pass, Gone, with the image
The ticket became CompletedP1: Closed, closed_reason = RepairedNone

If two months later the vehicle sees a pothole in the same place, a new P2 is created, and P1 stays as it is. Later the job puts P1 and P2 in one row in recurring_spots.
